# Agent Note: Official-tag source packages for portable releases

Status: implemented

English | [中文](2026-08-30-official-tag-source-packaging.zh.md)

## Problem

DeepSeek Harness can publish an official `dsh-v*` Git tag before the same version exists on npm. Treating npm as the portable build gate delays an already identifiable upstream release and makes the update promise depend on a second publication channel. Copying a built workspace is not an equivalent substitute: workspace links, unpublished peers, and build-machine paths can escape into the portable tree.

## Decision

Every automatic portable release starts from the highest official `deepseek-ai/deepseek-harness` `dsh-v*` Semantic Version tag and its exact 40-character commit. A read-only Ubuntu job checks out that commit with complete tag history, verifies the root and CLI versions plus the declared pnpm version, and runs the tagged checkout's own `release:verify`, `build:official`, `release:pack`, and `release:verify-packed-install` commands. The job packs the dsh family, vendored framework family, and Landlock entry exactly as the upstream release workflow does. It never receives repository write permission.

The job stages one artifact containing every official tarball, `provenance.json`, and `SHA256SUMS.txt`. Provenance binds the canonical upstream repository, tag, commit, dsh version, package manager, package identity, byte size, and SHA256 of every archive. Staging and both Windows consumers read each archive's `package/package.json`, reject duplicate or unexpected package names, reject residual `workspace:` dependency protocols, require one exact `@deepseek-ai/dsh` entry, require every dsh-family version to match the tag, and recalculate the complete file set and hashes. The Windows Server 2022 and 2025 builds download the same artifact generation.

The source job maps each packed manifest's declared repository directory to the corresponding importer in the official lockfile, verifies that importer's source package identity, and traverses production, optional, and required peer dependencies from `@deepseek-ai/dsh`. It excludes an unstaged optional internal package only when that package's source manifest explicitly rejects Windows x64. Every selected internal package becomes a local consumer root and override; exact external versions and parent-specific overrides come from the official lock rather than a fresh registry resolution. The job generates one canonical consumer manifest, workspace policy, and lockfile online, normalizes the proven Windows-incompatible optional entries, and then requires exact internal and external package metadata, registry resolutions, and runtime snapshots. The package model covers bundled dependencies, CPU, operating-system and libc rules, deprecation, engines, binary-entry presence, package identity, peer declarations, and peer metadata; the snapshot model covers dependency edges, ids, optional flags, optional edges, and transitive peers. A separate consumer-control model covers the lockfile version, root importer specifiers and resolved versions, root settings, every override, and every patched-dependency content hash. Unknown package, snapshot, importer, setting, override, patch, or root-lock fields fail closed.

Schema-4 provenance records that internal package set, the canonical runtime package-and-snapshot model and its SHA256, the consumer-control model and its SHA256, the Windows optional exclusions, required peer pins, and the byte size and SHA256 of all three consumer files. Each Windows build copies the complete input to disposable scratch space, repeats archive, provenance, consumer-file, graph, and lock checks, performs one frozen fetch from the official npm registry, and then installs the same lock frozen and offline into a hoisted tree. Pnpm's trusted-lock option is used only after the canonical lock's full-file hash and semantic models have been verified; this prevents its default release-age policy from consulting a machine-level registry during the offline phase. Package-manager manifests and build-machine `file:` locations are removed before assembly. The pnpm package is downloaded by exact version and pinned tarball SHA256. Package-manager install state stays in disposable `.build` and scratch directories; only the SHA256-verified pnpm download cache may persist under repository `.cache`, and that archive never enters the product. One clean pnpm payload and direct shim enter the runtime only so an explicit official `dsh plugin` command cannot fall through to Corepack or a global package manager.

Upstream build output can contain absolute checkout paths in non-executable CSS source-region comments and pnpm shim target comments. Portable assembly converts those source labels to repository-relative `packages/...` identities and removes the shim annotations without changing executable text, runtime configuration, or upstream behavior. Focused negative tests reject both annotation forms if any remain. Before compression, a binary-safe full-tree scan also rejects the actual repository, scratch, package-input, runner, and temporary paths in raw, slash-normalized, escaped, URI, UTF-8, or UTF-16 form.

The resulting manifest records the official source repository, tag, commit, package-manager version, complete and runtime package counts, external snapshot count, provenance hash, official source-lock hash, canonical consumer-lock hash, and runtime-model hash. Package verification requires one ZIP top-level directory, no pre-launch reparse points, an empty `dsh-home`, no default plugin or package-manager state, and drives the installed CLI with bundled Node.js to require `--version` to equal the selected dsh version. Release publication rechecks that the official tag has not moved, that it remains the highest tag for automatic runs, and that the portable allocation is unchanged. This source choice complements the [exact-ID Release publication decision](2026-08-30-exact-id-release-publication.md), which continues to own Draft isolation, asset identity, and the private-to-public transition.

The default product is CedarDSH Desktop. It builds the official tagged Harness source without code patches, then adds pinned Windows Node.js, pnpm, and Electron components, desktop lifecycle, portable data directories, and an explicit update notice. It contains and auto-installs no capability plugin. CedarDSH Model Probe is maintained and released from its own repository.

## Alternatives considered

**Wait for the exact npm package.** This preserves a published-package-only input but delays official tags indefinitely and failed for `dsh-v0.1.2-alpha.1`, which had a complete official release build before an npm package.

**Use `pnpm deploy` or copy the built workspace.** The deployed CLI does not materialize the complete peer and profile closure; an exact-tag trial failed at startup on a missing vendored Cordis package. Workspace copying can also retain links to the source checkout.

**Reimplement the upstream pack format.** A local packer would duplicate release policy and could diverge from upstream `files`, version rewriting, and prepack behavior. Invoking the tagged checkout's own commands keeps one definition.

**Install every tarball as a root dependency.** This is simple but includes packages that the CLI never reaches. Computing the internal graph from the CLI and materializing only that closure preserves the same verified source set and yields the smaller runtime tree.

**Generate the consumer lock again on Windows.** Even with exact root versions, a second resolver can reconnect already-present versions through different dependency edges, auto-install peers, or apply machine registry policy. Generating once beside the official source, hashing the complete consumer files, and comparing every runtime snapshot on Windows preserves one dependency decision.

## Consequences

An official tag can become a portable candidate without an npm publication. Source build time moves into one shared Ubuntu job, while the write-scoped publication job never executes upstream code. A tampered, incomplete, duplicated, moved, or version-inconsistent package input fails before Electron packaging. The same immutable package set feeds both supported Windows generations; the exact Windows 2025 ZIP selected for publication is then verified again on Windows Server 2022 and 2025, proving its CLI version and real Web startup.

The build now depends on the upstream release scripts remaining executable from their tag and on their declared package manager being available. If the upstream release process changes, the reusable source-pack job must follow that tagged process rather than silently falling back to npm or workspace copying. The optional npm input remains available only for local manual builds and is recorded distinctly in `manifest.json`.
