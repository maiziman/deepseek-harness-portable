# Agent Note: 按精确 ID 公开上游与插件 Release

Status: implemented

[English](2026-08-30-exact-id-release-publication.md) | 中文

## 问题

便携版构建依赖可安装的 `@deepseek-ai/dsh` 包，而官方项目通过 `dsh-v*` Git 标签公布源码版本，对应 npm 包可能稍后发布。因此只跟踪 npm dist-tag 可能错过官方预览版。GitHub Release 暂存还需要严格保持先私有、后公开：按标签选择的上传工具可能会先找到并修改已有公开 Release，后置校验无法撤销这次公开状态下的修改。PowerShell 读取 GitHub API 集合时必须先赋值再规范化，因为直接用 `@(...)` 包裹 `Invoke-RestMethod` 可能把整个 JSON 数组保留成单个嵌套元素。

## 决策

上游跟踪工作流从官方 `deepseek-ai/deepseek-harness` 仓库的 `dsh-v*` 标签中选择最高语义版本，并记录对应的 commit SHA。精确 npm 版本尚不存在时，任务正常结束且不进行构建。版本可以安装后，才进入两个 Windows runner 的构建和真实启动验证。便携版策略会在最高的完整公开严格 `v<语义版本>` Release 之后分配下一个补丁版本；历史 `v1.0.0` 至 `v1.2.0` 的标签与 ZIP 不一致是明确的迁移基准，之后的 Release 必须让标签、ZIP 和 `portable-version` 标记一致。精确 `dsh-version` 标记保证重复打包可幂等处理，也允许一个 dsh 版本对应多个便携补丁。公开前，工作流会在人工与自动流程共用的便携发布锁中再次确认官方标签仍指向记录的 commit、自动跟踪目标仍是最高版本、精确 npm 包仍然存在，并且便携版本分配没有变化。

Release 暂存由仓库自己的脚本按精确 GitHub Release ID 执行。每次运行都会使用隔离的临时标签和精确源码提交创建私有 Draft，只上传预期附件，并核对大小和 GitHub SHA256 摘要。暂存步骤会记录解析后的正文 SHA256；最终步骤会在公开前再次读取精确 ID、正文、源码提交和正式标签，然后在一次 API 修改中同时指定正式标签并把 `draft` 改为 `false`。生成的正式标签和 Release 记录的目标必须解析到同一个精确提交。自动说明位于固定身份前缀之后，并明确指定前一个便携标签；公开版本重跑时只核对这个稳定前缀，不要求 GitHub 再次生成逐字相同的说明。这套设计不会删除或替换任何 Release 附件：中断的运行可能留下私有的孤立 Draft，下一次运行仍可独立开始。完整的公开 Release 只接受校验，不进行写入。

便携包和模型能力插件使用独立的 Release 周期。人工创建的 `v*` 便携版标签把自身版本用作 `portableVersion`，并从标签提交内的文件读取精确 dsh 包版本；分支验证则在每次运行中只解析一次 npm `latest`。自动上游包也加入同一条递增的 `v*` 版本流。便携版发布说明会明确选择前一个使用严格 `v<语义版本>` 标签且附件完整的公开便携版，避免发布失败的标签、旧上游标签或插件标签改变比较范围。便携版 Release 只包含一个 ZIP 与 `SHA256SUMS.txt`；包内 dsh 是预览版时，GitHub prerelease 状态也会明确提示。插件标签使用 `plugin-model-capabilities-v<版本>`，只包含一个 npm 压缩包与 `SHA256SUMS.txt`，并在公开时关闭 GitHub Latest 状态，使项目主下载入口继续指向便携程序。

## 考虑过的替代方案

- npm `latest` 或 `next` 无法表示包仍在等待发布或刻意没有 dist-tag 的官方 Git 标签。
- 直接从每个源码标签构建需要复现上游 monorepo 的发布打包与完整依赖集合；等待官方精确 npm 包能够保持便携项目只使用已发布包的边界。
- 按标签操作的第三方上传 Action 无法在修改附件前证明目标仍是 Draft。
- 把插件压缩包加入每个便携版 Release 会耦合无关版本，并削弱两套双附件校验规则。

## 影响

官方源码标签可能已经出现在跟踪结果中，但暂时还无法制作便携包。Actions 概述会报告这个等待状态；每六小时检查一次，使精确 npm 包出现后无需 dist-tag 变化也能进入构建。桌面壳或内置插件修复可以在 dsh 不变时发布更高的便携补丁，已安装程序会比较这个便携版本。发布阶段遇到已完整公开的 Release 时只执行只读校验，绝不替换其附件。无网络策略测试会覆盖历史迁移基准、一个 dsh 对应多个补丁、未来 Release 附件不完整、身份不一致和来源标签移动。暂存失败可能留下隔离的私有 Draft，可以安全地人工删除，也不会阻塞之后的运行。

插件可以独立发布修复；由于插件 Release 不含便携 ZIP，桌面更新检查不会把它当作程序更新。公开前，插件工作流会在精确匹配的上游源码标签和提交中重复一次全新安装验证。Release 脚本集中复用附件和身份校验，每个工作流仍分别提供自己的标签、名称、正文、预览版策略和 Latest 策略。
