# Agent Note: 仅统计包内组件的首次启动进度

Status: implemented

[English](2026-08-30-package-owned-startup-progress.md) | 中文

## 问题

Web profile 首次启动时，需要在本地服务就绪前准备数百个依赖链接。固定计时无法反映这项工作；如果统计 profile 后备目录里的所有链接，还可能把构建机或用户解压目录上级 `node_modules` 中解析到的包算进去。

## 决策

桌面壳会立即打开独立的加载窗口，并依次展示运行时、profile、组件、服务和就绪阶段。构建会真实启动一次打包后的程序，只记录解析目标位于便携包自身 `app/node_modules` 内的 profile 链接数量。运行时进度采用相同的 realpath 过滤规则，因此便携目录上级的无关包不会改变完成数量。最终 ZIP 验证从空白主目录启动，捕获界面实际显示的组件分子、分母和机器可读状态，并要求显示总数、manifest 总数、实测包内链接、官方服务地址与最终界面全部一致。真实文件系统测试会创建包内 junction 与一个包外对照 junction，证明 Windows 上的目标过滤有效。

## 考虑过的替代方案

- 计时动画可以看起来平滑，但无法反映慢速磁盘、杀毒扫描或不同电脑的实际差异。
- 统计分发包内的全部文件衡量的是压缩包规模，而不是 profile 初始化进度。
- 统计 profile 后备目录里的全部链接会让外层开发工作区扭曲进度。

## 影响

首次启动进度来自已经完成的包内组件，ZIP 移动位置或改在其他目录解压后仍保持稳定。分发包外发现的可选包不会让进度提前完成，也不会显示超过清单总数的结果。上游依赖闭包变化会由下一次真实构建自动记录，不需要硬编码组件数量。
