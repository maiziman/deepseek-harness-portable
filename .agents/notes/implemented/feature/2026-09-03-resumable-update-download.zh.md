# Agent Note：更新下载断点续传

Status: implemented

[English](2026-09-03-resumable-update-download.md) | 中文

## 问题

桌面更新器总是从第 0 字节开始下载发布 ZIP。关闭进度窗口、退出程序或一次瞬时网络故障都会丢掉已下载的全部内容，每次重试都要从头再来——对数百 MB 的安装包和慢速网络来说代价很高。

## 决策

更新器把下载固定在 `.cedardsh-update/<版本>/work` 这个按版本隔离的稳定路径下，使断点文件能跨程序重启存活；各次尝试复用同一个暂存目录，而不是每次新建 `run-*` 临时目录。下载写入 `<资产名>.partial`；保留的断点文件用 HTTP `Range: bytes=<偏移>-` 请求续传，跨 GitHub 重定向时重新附加该请求头。续传响应必须是 `206`，且 `Content-Range` 的起点精确等于偏移、总长度等于发布的资产大小；返回 `200` 表示服务器忽略了 Range，则从零重新开始。SHA-256 覆盖整个文件：续传时先对已有前缀做哈希再追加，因此最终摘要仍校验完整资产。中断的传输保留断点文件供下次续传；只有大小或摘要校验失败的传输才丢弃它。进度窗口现在可以关闭；关闭窗口会中止进行中的请求、保留断点文件并抑制失败弹窗，下次更新会显示并从保存的进度继续。已完成的压缩包通过摘要侧车文件跨尝试复用，防止发布资产被重新上传后误用旧包；开始新更新时会清理其他版本或旧构建遗留的暂存目录。

## 备选方案

- 关闭窗口后继续后台下载会掩盖失败，并可能在用户不知情时重启应用。
- 中断即删除断点文件保持原有简单性，但每次都要重复完整下载的开销。
- 把哈希状态序列化到侧车文件可避免重读前缀，但依赖不稳定的运行时格式。
- 服务器忽略 Range 时一律重新下载能让代码最少，但会失去在不支持 Range 的中间层上的续传收益。

## 影响

关闭进度窗口是暂停而非放弃下载；再次打开更新会从同一字节偏移继续，已完成的部分跨应用重启仍然保留。每个响应都会校验 GitHub 重定向与 CDN 响应，续传不可能悄悄拼接其他资产或大小的字节。中断的尝试只在 `.cedardsh-update` 下留下有界残留，会在下次更新时或由独立安装交接流程清除。
